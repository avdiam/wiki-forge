## On your proposals

### 1. Python CLI Wrappers — Partially agree, but be careful

The idea of `python wiki-query.py "what is attention?"` sounds clean but has a fundamental issue: **the judgment step can't be in Python.** The scripts do mechanical work (index, search, lint). The LLM does the synthesis, contradiction detection, page writing. A Python orchestrator would either:

- (a) Call an LLM API internally — making it a full application, not a plugin. Now you need API keys, billing, model selection, etc. That's a different product.
- (b) Just be a wrapper around the existing scripts — which the LLM can already call directly via Bash.

I think (b) is what we actually want, but framed as **documented workflows** rather than Python wrappers. The LLM reads the instructions, calls the scripts, does the judgment. No new code needed.

**What I'd keep from this idea:** A single entry-point script that prints available commands and usage, like a `wiki-forge help` CLI. Useful for any LLM that can run `python wiki/.scripts/help.py`.

### 2. Context-Forking Fallbacks — Strong agree

This is the real gap. Claude Code's `context: fork` is what makes large ingests safe (heavy file reads happen in a subprocess, not the main session). Other tools don't have this.

The fallback is exactly what you said: **explicit context management instructions in AGENTS.md.** Something like:

> "When ingesting a source, read it fully, then summarize key claims before proceeding to edit pages. If your context window is getting full, complete the current page edit, commit, and then continue with the next edit in a fresh mental state. Do not try to hold the full source + all target pages simultaneously."

This is a soft equivalent — it won't be as clean as context forking, but it's the best we can do without platform-specific features.

### 3. Native Context Files — Agree, low effort, high value

Generating `.cursorrules`, `.windsurfrules`, etc. during `wiki-init` is a great idea. These can be thin pointers:

```
# .cursorrules
# Wiki Forge — see wiki/AGENTS.md for full schema and operational rules.
# Helper scripts are in wiki/.scripts/ — run them via terminal.
# See wiki/WORKFLOWS.md for step-by-step operational instructions.
```

Minimal content, just enough to hook the tool into the right files.

## Combined proposal

Here's what I think we should build:

### A. `WORKFLOWS.md` (new file, installed by wiki-init into wiki/)

A universal, LLM-agnostic instruction file that describes every operation as step-by-step instructions using shell commands + LLM judgment. No Claude-specific tool names. Sections:

1. **Ingest a source** — step-by-step with script calls
2. **Query the wiki** — threshold check, search/index read, synthesis rules
3. **Lint the wiki** — three-pass workflow with script calls
4. **Capture from URL** — fetch, normalize, write to vault, then ingest
5. **View the log** — grep commands

Each workflow references `AGENTS.md` for the schema rules and templates.

### B. Context management section in AGENTS.md

Add a section called "## Working without context forking" that gives LLMs practical guidance on managing large operations without blowing their context window.

### C. Tool-specific context files (generated by wiki-init)

During init, generate thin pointer files:
- `.cursorrules` — for Cursor
- `.windsurfrules` — for Windsurf  
- A note in AGENTS.md about Aider's `.aider.conf.yml`

These just point to `AGENTS.md` and `WORKFLOWS.md`.

### D. Update wiki-init SKILL.md

Add a step to generate the above files during initialization.

---

## What we should NOT do

- **Python orchestrators that call LLM APIs** — that's a different product
- **Per-tool skill files** — fragile, high maintenance, each tool updates independently
- **Rewrite CLAUDE.md/AGENTS.md to be lowest-common-denominator** — Claude Code users should keep the full power of skills/agents

The Claude-specific skills and agents stay as-is. The new files supplement them for other tools.
